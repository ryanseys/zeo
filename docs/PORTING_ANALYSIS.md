# Porting Spinel to Rust: feasibility analysis and spike report

This document captures the feasibility analysis behind `zeo` and reports
on what the Phase 0 spike actually built, including where implementation
diverged from the original design (macro_rules! authoring is iterative, and a
few things only became clear once real code had to compile).

Spinel (referenced here read-only) is a whole-program AOT
Ruby-to-C compiler: ~75K LOC of C compiler (`src/`) plus a ~24K LOC C runtime
(`lib/`). This repo is a spike proving that the same architecture can be
rebuilt in Rust, generating Rust instead of C, with `send`/`define_method`
genuine open-world dynamic dispatch designed into the core from the start
(something zeo itself never has).

## Feasibility findings

1. **Architecture ports cleanly; breadth is the real cost.** Spinel's shape
   -- text AST bridge from a parser, flat/dynamic node arena, whole-program
   monotonic type-fixpoint, printf-style codegen against a runtime library --
   is compact and portable. The 75K/24K LOC total is not algorithmic depth;
   it's ~2,000+ hand-coded `(receiver-type, method-name, arity)` special cases
   in `codegen_call.c`/`codegen_call_recv.c`. A full port would be dominated
   by mechanical breadth, not architectural risk.

2. **Spinel's own 1,729-test golden corpus (`test/*.rb` + `.rb.expected`) is
   directly reusable** as a conformance suite for a Rust port -- every fixture
   is oracle-verified against real `ruby` and has no dependency on Spinel's C
   internals. This is the single biggest de-risking factor for a real port
   beyond this spike.

3. **The type system and monomorphization strategy is a great match for
   Rust.** Spinel's `TyKind` (a flat C int enum, `TY_POLY` as the boxed
   escape hatch) is exactly what a native Rust `enum` expresses more safely.
   Spinel's 4 Array representations / 7-9 Hash representations map directly
   onto Rust generics/enums instead of hand-duplicated C structs.

4. **`cls_id`-switch dispatch generalizes to `match` on an enum
   discriminant.** Spinel never uses a runtime vtable -- single inheritance +
   module MRO is resolved entirely at compile time, and polymorphic call
   sites compile to a freshly generated, whole-program-closed `switch(cls_id)`
   over only the classes actually instantiated in that program. Elegant and
   fast, but fundamentally closed-world.

5. **GC rooting and exceptions are genuine architectural rewrites, not
   transliterations.** `SP_GC_ROOT` is a manual shadow-stack convention with
   no static enforcement -- a silent-use-after-free footgun that has no
   honest C-to-Rust translation (it has to become `Rc`/`RefCell`, or a real
   arena/tracer later). `setjmp`/`longjmp` exception handling is fundamentally
   un-Rust-like and would become `Result`-based propagation touching every
   generated function signature -- out of scope for this spike (no
   `raise`/`rescue`/`ensure` needed by the 7 examples).

6. **`send`/`define_method`/`method_missing` are NOT real dynamic dispatch in
   Spinel today.** Every one of these degrades, at compile time, into a
   direct AST rewrite (literal name), a closed if-chain over every
   symbol/string literal in the whole program (non-literal name), or a hard
   compile-time rejection (`method_missing` is never actually invoked --
   only a build warning is printed). There is no runtime method table
   anywhere in Spinel's generated code or runtime. This is exactly why
   zeo's object model deliberately diverges here -- see below.

## The one deliberate architectural divergence: real dynamic dispatch

Spinel's dispatch is always compile-time-resolved: a direct call, or a
`switch` on a `cls_id` tag generated by enumerating the compiler's own
whole-program-known class list. zeo keeps that as the *default* path
(mirroring `comp_method_in_chain`, `compiler.rs`'s `Compiler::method_in_chain`)
but adds a second path zeo never has: `zeo-rt`'s `ClassRegistry` is a
real, mutable, `Symbol`-keyed method table per class, populated at program
startup and consulted only when the compiler can't resolve a call statically.
`send`/`method_missing` are implemented against this table for real, not
simulated via program-literal enumeration.

Two Rust idioms did almost all of the work:

- **Concrete-type-by-default, `dyn Trait`-only-on-erasure** is the exact
  Rust-native analog of Spinel's "monomorphic `TyKind` by default, `TY_POLY`
  only on unification failure." Codegen keeps a value's concrete class
  (`Point`, `Greeter`, ...) for as long as it can, only erasing to
  `Rc<dyn RubyObject>` (`RObj`) when a value genuinely flows into a dynamic
  context (`send`'s argument).
- **Per-field `RefCell<RubyValue>` interior mutability** lets every generated
  method take `&self` uniformly (no separate const/mut channel), matching
  Ruby's own "everything is mutable through self" semantics, while narrowing
  the one real cost (a `RefCell` panics on a double-borrow) to individual
  ivars instead of a whole-object lock.

## What got built (Phase 0 spike)

All 7 example programs compile through the full pipeline (`ruby-prism` parse
→ `Hir` lowering → `analyze` registration → `codegen` Rust-text emission →
`cargo build` against `zeo-rt`) and produce byte-identical stdout to real
`ruby`, verified by `cargo test -p zeo --test examples`:

| Example | Proves |
|---|---|
| `hello.rb` | End-to-end pipeline shape; Symbol literal handling. |
| `arith.rb` | Unboxed `i64` literal arithmetic (`zeo_rt::int_add`, the `sp_int_add` analog). |
| `ivars.rb` | Real per-instance state via `ruby_class!`-generated named fields, static dispatch. |
| `inheritance.rb` | `super` (statement inlining), static dispatch surviving alongside the dynamic path. |
| `blocks.rb` | Known-shape block inlining (`3.times` → a native `for` loop, zero closures). |
| `dynamic.rb` | **The centerpiece**: `define_method` + a genuinely non-literal `send` target, routed through the real `ClassRegistry`. |
| `method_missing.rb` | The miss → superclass walk → `method_missing` fallback chain, which Spinel never implements at all. |

Zero `unsafe` code anywhere in `zeo` or `zeo-rt` (parsing safety is
fully delegated to the `ruby-prism` crate, which does its own FFI
internally).

## Implementation notes / where the plan and reality diverged

Writing real code surfaced several things the design sketch didn't (or got
slightly wrong) -- worth recording so they aren't rediscovered later:

- **`macro_rules!` hygiene and `self`.** A literal `&self` hardcoded in the
  macro's expansion template doesn't hygienically unify with a `self` written
  inside a caller-supplied `$body:block` -- they're different tokens from the
  macro's perspective even though they're spelled identically. Fix: capture
  the receiver as `$slf:tt` from the caller's own tokens instead of
  hardcoding it, so both the signature and the body's usage trace back to the
  same source.
- **`as_any()` can't have a default body.** `trait RubyObject: Any { fn
  as_any(&self) -> &dyn Any { self } }` looks like it should work as a
  default method, but rustc type-checks default bodies generically over an
  unsized `Self`, so the coercion to `&dyn Any` fails. Each concrete impl
  needs its own one-line body (the macro generates it) -- the trait method
  itself stays undefined, just declared.
- **`RubyObject: Any` supertrait upcasting** (`&dyn RubyObject` → `&dyn Any`)
  is stable as of Rust 1.86, but the spike uses an explicit `as_any()` trait
  method instead of relying on it, for robustness across a wider MSRV range
  and because it reads more explicitly at the call site.
- **Uniform `RubyValue` return type, never `()`.** Every generated method
  returns `RubyValue`, never omitted -- Ruby methods always implicitly return
  something (the last expression, or nil), so `initialize` and friends
  explicitly end with `RubyValue::Nil` rather than introducing a separate
  "void method" case that the trampoline signature (`fn(&RObj, &[RubyValue])
  -> RubyValue`) would need to special-case.
- **`super` is inlined, not called.** Spinel's C subclasses share a struct
  layout with their parent (a "common initial sequence" trick), so
  `Animal_speak((Animal*)self)` type-checks even when `self` is really a
  `Dog*`. Rust has no such structural-subtyping escape hatch between two
  unrelated structs, so `super` is implemented by splicing the resolved
  parent method's body directly into the call site. This is a real zeo
  mechanism too (`emit_super_inline`), just used there as a `yield`-triggered
  optimization rather than the default.
- **`TyKind` almost went unused.** The first working version of `codegen`
  didn't route through `types::infer_type` at all -- it just pattern-matched
  `HirNode::New` directly wherever a receiver's class was needed, which
  worked but left the `TyKind` enum dead code. Refactored so
  `infer_class`/dispatch decisions go through a real (if currently trivial)
  `infer_type` function, keeping the type-system architecture the port is
  meant to validate actually load-bearing rather than decorative.
- **Two `LocalWrite` emission sites had to share code.** The first cut had
  `fn main()`'s top-level statements calling the generic expression emitter
  directly, which wrapped `let name = ...` in a throwaway block -- scoping
  the binding out of existence before the next statement could read it
  (caught by `dynamic.rb`, which assigns `name = :hello` then reads it two
  lines later). Fixed by factoring a single `emit_statement(cx, stmt,
  is_tail)` used by both method bodies and `fn main()`, rather than
  duplicating the special-case.

## Scope-cuts made deliberately for this spike

- **Every ivar/param/return is `RubyValue` (boxed) except literal `Int`
  arithmetic.** Spinel's real per-slot monomorphization (deciding which
  locals/ivars can be native `i64`/`f64`/etc.) is a genuine performance
  optimization, but it's orthogonal to proving the pipeline shape and the
  dynamic-dispatch core -- deferred to Phase 1.
- **No fixpoint loop in `analyze`.** A single top-to-bottom pass is enough
  for the 7 examples (no forward references, no mutual recursion between
  inference results). The pass is structured as one function walking the
  whole program and mutating a `Compiler`, which is exactly the shape a real
  fixpoint would wrap in `for iter in 0..128 { ... }` later.
- **`Symbol` is pure runtime interning** (a `HashMap`), not Spinel's split of
  a codegen-baked static table plus a small dynamic pool. Every literal and
  every runtime-computed symbol goes through the same intern call.
- **No `Array`/`Hash`/`Float`/`String`-as-a-mutable-type/`Bignum`.** Only
  what the 7 examples need.
- **No `raise`/`rescue`/`ensure` from Ruby source.** Only the minimal
  "uncaught dispatch failure prints and exits 1" behavior needed by
  `method_missing.rb`'s total-miss path.
- **No inherited ivars.** Every class's `ivars` list is its own; a subclass
  that both defines ivars *and* needs its parent's ivars (not exercised by
  any of the 7 examples) isn't handled yet.

## Phased roadmap beyond the spike

1. **Breadth**: expand `TyKind`/`Hir`/codegen to cover more of Ruby, using
   Spinel's `test/*.rb` + `.rb.expected` corpus directly as the conformance
   suite (see finding 2) -- this is the highest-leverage next step since it's
   pure execution, no new design risk.
2. **Real ivar/param/return monomorphization** -- the `TyKind` fixpoint,
   generating native-typed struct fields instead of uniform `RubyValue`,
   mirroring Spinel's actual performance story.
3. **GC decision**: stay on `Rc` (accepting cycle leaks) vs. build a real
   arena + mark-sweep collector with generational indices.
4. **`Result`-based exceptions**: `raise`/`rescue`/`ensure`/non-local
   `break`/`return`, replacing Spinel's `setjmp`/`longjmp` model with
   `Result<RubyValue, RubyException>` propagation via `?`.
5. **Classes/modules/mixins at Spinel's fidelity**: `include`/`extend`/
   `prepend`, inherited ivars, `respond_to?`, reflection.
6. **A real escaping `Proc`/closure runtime type** -- only needed once a
   block is stored or passed onward instead of consumed immediately by its
   invoking method (the 7 examples never do this).
